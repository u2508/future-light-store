**Purpose:** classify only existing Shopify products into the right existing family/product-type collections. This document does not authorize new-product intake, copy/SEO changes, price or inventory changes, product deletion, taxonomy/metafield edits, collection creation/deletion/renaming, Google Merchant Center/feed changes, or theme changes as part of classification. The user clarified that the supplied DOCX is for product-to-separate-collection classification only. The user later authorized the normal release workflow as the final operational task, after classification is complete, with a preservation gate for the classification and product details protected by this work. The user also authorized pushing and deploying both the web repository and Shopify theme repository after the release; these are post-release delivery tasks and do not permit unrelated dirty changes to be included.

## Remaining DOCX rules and how this task uses them

The source DOCX is a product-intake guide as well as a search library. Its complete guidance is preserved here for traceability, but it does not override the user's current “no more products” instruction or the existing-product-only classification scope.

### Hard exclusions and existing-catalog treatment

The DOCX excludes batteries, rechargeable cells, power banks, portable chargers, battery packs and products whose core function depends on an unverified battery; logic boards, bare boards, replacement boards, repair parts and spare assemblies; medical devices/diagnostic or treatment claims, supplements, ingestibles and medication; adult/erotic/sexual-wellness/fetish/weapon/tactical-weapon/counterfeit or unsupported licensed-character products; stock below 200, missing price/cost/images, unusable images, unclear variant mapping or materially misleading supplier copy; and duplicates or options that expose supplier SKU codes rather than shopper-readable attributes.

For this existing catalog task, these are review/hold signals only. They do not authorize deletion, unpublishing, price/inventory adjustment, image replacement, or any non-tag Shopify write. In particular, a replacement/repair part already in Shopify is not to be routed as a family-store product simply because it is present; if no honest existing topical collection fits, remove only confirmed false routing tags and retain a visible review hold. The user's separate “no replacement/repair products” instruction applies prospectively to intake; this plan does not add products.

### Source qualification score

The DOCX proposes this 100-point intake-readiness rubric. For collection decisions, visual/evidence quality, store fit, and variant clarity may help prioritize human review; the score is not an automatic classifier, a tag rule, or authorization to change a field. Commercial-fit and content-readiness criteria do not authorize pricing, SEO, or copy writes in this classification task. No weighted score can override a hard exclusion or a visual/identity conflict.

| Source dimension | Points | Evidence named by the DOCX | Current use |
| --- | ---: | --- | --- |
| Evidence quality | 0–30 | Main image/product match, visible variants, supported dimensions/material/use, no dominant supplier watermark or China-focused scene | Human review priority; images/options must still be inspected product by product. |
| Store fit | 0–20 | Family-safe/giftable/useful, target collection alignment, explainable product | Tests lane and exact collection fit; does not substitute for Shopify's live rule. |
| Commercial fit | 0–20 | Stock ≥200, stable cost, plausible US price, healthy margin after store overhead, no commodity race-to-bottom | Intake-only; no current price, cost, margin or inventory mutations. |
| Variant clarity | 0–15 | Shopper-readable color, size, pack count or style; remove codes only when the meaningful attribute is known | Flags confusing variants for a separate, explicitly authorized review; do not rename variants here. |
| Content readiness | 0–15 | Verified facts for product-specific title, description, FAQ, alt text and collection placement | Content field is preserved exactly in this workstream; do not generate or overwrite copy. |

The source sequence is: search one family with visible US/stock/family/safety filters; inspect primary and variant images; check cost, US price, stock, shipping, and readable option names; deduplicate against Shopify and DSers; add controlled batches and confirm import readback; then classify after Shopify readback. Steps 1–5 are out of scope now because the user said no more products should be added. The only applicable handoff principle is to classify existing Shopify records from a complete live readback, which this plan does with exact product/collection preimages and per-cohort reconciliation.

### SEO, GEO, AEO, FAQs and image-alt guidance (preservation only)

The DOCX says titles should lead with the product type, then verified differentiators such as material/size/use/included set, avoiding supplier years, duplicated phrases, random brands and SKU codes. Descriptions should sound human, say what the exact item is, what it helps the shopper do, what is included and confirmed limits, without generic filler. Facts must come from verified title/image/variant/specification/shipping evidence; normalize HTML entities and duplicate fields. FAQs should answer fit, size, material, compatibility, care, included pieces and context without invented certifications/performance guarantees. GEO/AEO copy should use concise answer-ready summaries, explicit product nouns, natural synonyms, scannable headings and accurate structured data/internal links. Alt text must describe the actual item and meaningful variant, not a generic lifestyle scene; mismatched media is a visual-review hold.

These rules are included because the user asked for the source data in the plan, not as permission to rewrite current product copy. Existing accurate/approved title, description, SEO title/description, variant labels and image mappings are byte-preservation fields for the future release. Any separate SEO-writing project needs its own explicit scope and per-product evidence/review gate.

## Classification decisions and evidence policy

1. Assign one primary DOCX lane per product only when identity is sufficiently clear. Route it to the narrowest accurate existing Shopify collection. Secondary collection membership is allowed only when its purpose still fits the item and the exact secondary collection is named in the proposal.
2. `hold` when identity, intended use, exact variant set, audience, image-to-item match, or target collection is ambiguous or conflicting. Do not “solve” an empty lane by misrouting products.
3. Keep good, product-faithful media and all accurate existing metadata. Do not change title, description, SEO, product type, Shopify category/metafields, price, compare-at price, inventory, status, publication, images, or variant mappings in this workstream.
4. Existing smart collections are tag-driven. A repair may add/remove only the exact routing tags for the named collection changes. Preserve all other tags; in particular, do not sweep words such as `pets`, `general`, `lighting-decor`, or a product-family tag just because they look suspicious. A tag may be removed only when it is the confirmed rule for an explicitly identified incorrect collection, or when it is the `classification-review` marker on a product whose reviewed destination tags and exact memberships are verified in the same operation. If one exact tag also matches an explicit tag-only OR collection rule, enumerate every resulting collection membership in the manifest; no rule-induced membership may be left unaccounted.
5. No keyword sweep, broad “cleanup” or blanket lane assignment. Use the full product GID, complete product/media/variant/membership snapshot, current exact tags, and independent visual review. Score or confidence can prioritize review but can never turn uncertain evidence into a write.

### Fail-safe writer requirements

- Require the exact Future Light domain, live Shop GID, API version, both snapshot hashes, a reviewed manifest, exact product GIDs, and exact old tag/membership preimages.
- Validate that each collection change is justified by a live exact `TAG EQUALS` rule, either as a single-rule collection or as one member of an explicit tag-only OR rule; enumerate every destination driven by the tag. Reject fallback collection, any product ID not in the manifest, every non-tag field, duplicate product, unknown collection, confidence below the chosen threshold, and snapshot drift.
- Use `tagsAdd` and `tagsRemove` rather than replacing the entire tag list; never write Shopify categories, metafields, media, status, publication, or copy. Use one serial writer, a scoped lock, persisted per-product receipts, idempotent retries, and read-only reconciliation after any ambiguous timeout.
- A successful API response is not completion. Poll/read back exact tags and collection membership, then compare title, description, SEO, category, type, status, inventory, variant IDs/options/prices, media IDs, and publication to the preimage. On mismatch, stop and report; do not auto-delete or “repair back” any unrelated state.
- Keep the workflow independent of `npm run release`, release checkpoints, SALT systems/credentials/processes, Google Merchant Center and the supplier/DSers intake. Use the already authenticated Shopify CLI session; never extract or print its token.
