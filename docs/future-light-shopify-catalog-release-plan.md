# Future Light Shopify Catalog Release Plan

## Purpose

Build one dependable Future Light release workflow that can source qualified additions from DSers, improve the Shopify product catalog, and be operated from a native macOS control surface. The attached DSers search-term document is the sourcing-policy authority. Shopify is the only commerce system in scope: this plan does not access or change Google Merchant Center, Google feed settings, or Google-specific sales-channel metafields.

The release must not conflate new-product sourcing with the repair of products already in Shopify. The DSers stock, supplier cost, and duplicate gates apply to new candidates only. The catalog-quality pass covers every product record in the confirmed store, including non-active records, while preserving each product's existing status, sales-channel publication, inventory, and price unless a separate, exact approved policy says otherwise. Customer-facing collection membership is limited to eligible active products. This task does not build/deploy the public Vite site or theme, write Google-specific fields, upload a feed, or access Google Merchant Center.

### Current Shopify API constraints checked 2026-09-24

- The repository defaults most Shopify Admin clients to API `2026-07`, but a few older scripts default to `2026-04`. A release must freeze one explicitly selected API version in its input fingerprint and reject mixed-version writers. Shopify's `2026-07` collection model is materially different: a collection can combine condition sources, manual selections, exclusions, subcollections, and app-owned sources. A readback that checks only legacy `ruleSet` or custom/smart type is incomplete. The collection adapter must query `Collection.sources` with inline fragments, preserve source IDs, and apply inclusion/exclusion deltas to the exact source. See [Shopify's collection model](https://shopify.dev/docs/apps/build/product-merchandising/products-and-collections/use-new-collections-model) and [migration guide](https://shopify.dev/docs/apps/build/product-merchandising/products-and-collections/migrate-to-flexible-collections).
- For repair of existing products, prefer narrow `productUpdate`, variant-specific mutations, and media association mutations. Do not use `productSet` as a partial merge: Shopify documents that its option/variant lists are replaced as complete state, and omitted entries can be removed. An apply manifest must state every field it will write; any array-replacement mutation requires a complete frozen before-image and an explicit diff. See [Shopify product sync semantics](https://shopify.dev/docs/apps/build/product-merchandising/products-and-collections/sync-data).
- Metafield writes must be exact, typed, and concurrency-safe. `metafieldsSet` is atomic, accepts at most 25 metafields per call, and supports `compareDigest`; use the fetched digest for updates and `null` when asserting a new key is absent. A mismatch is a conflict and must be re-read/replanned, never retried as a blind overwrite. After the write, independently read back owner ID, namespace, key, type, value/reference ID, and compare digest. See [Shopify `metafieldsSet`](https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldsSet).
- Taxonomy classification must resolve an exact active leaf node, not a text similarity or root fallback. Freeze its ID and full path; read back both. Category attributes are a union of typed Shopify taxonomy-attribute forms, so GraphQL queries must use correct inline fragments instead of selecting union fields directly. Keep product-category assignment approval distinct from category-metafield approval. See [Shopify taxonomy categories](https://shopify.dev/docs/api/admin-graphql/latest/objects/TaxonomyCategory) and [product update fields](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/ProductUpdateInput).
- Use bulk operations for complete catalog exports, then validate root product counts, object counts, pagination/record coverage, and snapshot fingerprints before transforming data. The bulk result is asynchronous JSONL; poll the operation to a terminal status, checkpoint its ID, and download completed or partial results before their seven-day URLs expire. Use parallelism for independent local image/SEO analysis; keep one mutation coordinator, obey API throttling, and never concurrently write the same product. See [Shopify bulk operations](https://shopify.dev/docs/apps/build/apis/graphql-admin/bulk-operations/queries).
- On-page product structured data is in scope only insofar as it truthfully matches visible product/variant options, prices, availability, and canonical URLs. Google Search Central documents `ProductGroup` and variant relationships for variant products; this is public SEO documentation only, not permission to access Merchant Center, edit feeds, or write Google-specific Shopify fields. Never promise indexing or rich-result display. See [Google product variant structured data](https://developers.google.com/search/docs/appearance/structured-data/product-variants) and [ecommerce structured data](https://developers.google.com/search/docs/specialty/ecommerce/include-structured-data-relevant-to-ecommerce).

### Hard exclusions

The following six rules are retained verbatim from the DOCX; a high score never overrides them:

1. “Batteries, rechargeable cells, power banks, portable chargers, battery packs and products whose core function depends on an unverified battery.”
2. “Logic boards, bare boards, replacement boards, repair parts, spare assemblies and products marketed for device repair.”
3. “Medical devices, diagnostic claims, supplements, ingestibles, medication, cosmetic claims that promise treatment or guaranteed outcomes.”
4. “Adult, erotic, sexual-wellness, fetish, weapon, tactical weapon, counterfeit, trademark-infringing or licensed-character items without credible evidence.”
5. “Products with stock below 200, missing price/cost, missing images, unusable images, unclear variant mapping or materially misleading supplier copy.”
6. “Duplicate products already pushed to Shopify, near-duplicates with no meaningful differentiation, and variants whose names expose supplier SKU codes instead of shopper-readable attributes.”

Also hold chargers if the relevant certification evidence is unclear, and reject cosmetic claims promising treatment or guaranteed outcomes. Require an explicit US shipping destination, and when per-variant stock is supplied, use the lowest verified option stock; missing inventory for any option is a hold, even if the product aggregate is high. Candidate checks must be backed by evidence records rather than free boolean assertions. New-product rejection never triggers deletion of an existing Shopify product.

### Qualification score

The versioned policy preserves these five DOCX criteria and weights exactly:

| Criterion | Points | Source criterion |
| --- | ---: | --- |
| Evidence quality | 0–30 | Primary image matches the product, variants are visible, dimensions/material/use are supported, and no supplier watermark or China-focused scene dominates the listing. |
| Store fit | 0–20 | Family-safe, giftable or useful, aligned with the target collection, and easy to explain in natural language. |
| Commercial fit | 0–20 | Stock ≥200, stable cost, plausible US price, healthy margin after the store overhead, and no obvious commodity race-to-the-bottom. |
| Variant clarity | 0–15 | Color, size, pack count or style is shopper-readable; remove codes and preserve only meaningful option structure. |
| Content readiness | 0–15 | Enough verified facts for a product-specific title, description, FAQ, alt text and collection placement without inventing claims. |

Use the total to rank review; the DOCX defines no minimum passing score, so none is invented. A hard exclusion always rejects regardless of points. Separately, for live selling-price review, include the user's stated $16 per-order overhead and $13 per-order paid-acquisition cost (planning assumptions, not verified live campaign figures), plus verified landed product cost, shipping, discounts, and payment costs where available. Refresh variable costs from authoritative current records; missing cost or market comparison means hold the price recommendation.

## Shopify catalog quality workflow

1. Load only the explicitly configured Future Light Shopify target. Fetch and freeze every product record and its status, all product media, all variants/options, current category/metafields, inventory, and last-verified content fingerprint. Separately derive the active, channel-eligible subset used for collections. Do not infer current target counts from an older snapshot.
2. Inspect every product gallery image and each variant-to-image association. Scripts may fetch, checksum, paginate, deduplicate, and arrange images for review, but may not approve, reject, or select a “closest” variant image. A model/human reviewer must inspect each original image and each proposed source-to-variant association and record a decision against exact product, variant, and media IDs. Contact sheets may assist navigation but never replace inspection of individual originals. Keep suitable existing images. Generate a replacement only when the original is broken or materially inappropriate, then compare it beside the source and verify the exact same sellable item, parts, shape, color/finish, and included accessories; if faithfulness cannot be established, hold the listing instead of substituting a different product.
3. Produce a per-product evidence ledger. Attribute claims to verified Shopify/supplier facts or clear visual observations. Images support only visible identity, shape, color, pattern, and legible packaging text—not material, measurements, compatibility, safety, certifications, origin, health, or performance claims.
4. Before drafting, independently classify the live title and description as `approved_keep`, `needs_rewrite`, or `held`; bind the decision to the original text hash and source-evidence fingerprint. Preserve `approved_keep` copy byte-for-byte. Rewrite only `needs_rewrite` records from independent product/image/variant evidence; never let proposed copy validate itself, and never substitute a generic fallback. Ambiguous support or identity becomes `held`. Draft readable product-first titles, detailed human descriptions, concise SEO fields, scannable answer-ready copy, and specific alt text. Remove supplier boilerplate, SKU codes, duplicated fields, HTML entities, unsupported gender/category language, and generic filler. Keep visible product content and structured data aligned.
5. Propose the Shopify product category, category metafields, product metafields, variant option labels, and image mappings using Shopify's accepted definitions and enumerations. Preserve good images and the exact product identity. Generate a replacement only for a clearly inappropriate/broken asset with a source-identity guard; hold ambiguous mappings instead of guessing.
6. Every fresh release run starts at step 1 with current Shopify-target verification, then takes a fresh complete read snapshot and evaluates its exact frozen manifest; it must not silently resume a saved run. `--resume` is a separate explicit operator mode and is allowed only when exact target, manifest, graph, stage order, source hashes, and all prior readback receipts still match. Apply changes through a Future Light-only Shopify client, reconcile after timeouts, and read every changed product back from Shopify. For title/description/SEO, compare the pre-write fingerprint to the approved manifest, skip `approved_keep` and unchanged values, and fail closed on generic/self-evidenced or unsupported copy; no stage may replace accurate copy with a fallback. Verify the written strings exactly on Shopify before marking the record complete.
7. Reconcile storefront collections independently: New Arrivals may contain up to the 500 most recently updated eligible active products, sorted by verified `updatedAt` with `createdAt` and stable ID tie-breakers; Best Sellers may contain up to 250 products ordered only by verified order/line-item sales data. Never pad Best Sellers with merely new products, and remove any conflicting 300-product release minimum. For every managed collection, verify exact Shopify collection ID, rule/manual behavior, eligible product IDs, count, and visible Storefront API membership; keep genuinely empty collections empty or hidden rather than populating them with unrelated products.
8. Keep the Judge.me reviews widget on the PDP Reviews tab as a separate storefront integration gate. This is a headless React storefront: Judge.me documents its platform-independent (external-page) widget as Awesome-plan-only, requiring platform-independent widgets enabled in Settings > Advanced, a store-generated script, and the legacy Review Widget markup. The Shopify Liquid snippet alone is not sufficient. Verify the exact generated bootstrap, rendered tab, and review data on the confirmed storefront; a bare placeholder is not proof of integration. Do not fabricate reviews or counts.

## Release and operator architecture

- Keep only `npm run release` and `npm run release -- --resume` as release operator commands. Both invoke one guarded graph: frozen new-product cohort work, then the all-active Shopify quality pass, then final Shopify readback. The active-catalog pass must not run the unrelated broad-profile deletion, price-rework, collection-merge, collection-shuffle, web/theme build, or Google/Merchant Center work. Do not change the aliases until the replacement runner is independently tested.
- Build a dedicated Future Light supervisor API with identity, state, paged logs, start, resume, and stop. Bind to loopback, require a per-install mutation secret, validate host/origin, accept only fixed actions/profile and an explicit Future Light checkout, and never accept an arbitrary command, root, environment, or PID from the UI.
- Acquire the run lock before any Shopify synchronization/preflight. The supervisor owns the launched process group. Cooperative stop writes an `interrupted` checkpoint; resume accepts it only after verifying the frozen cohort and input fingerprints. Never stop a process by trusting a stale PID in a checkpoint.
- Port the source SwiftUI screen as a separate native macOS app target. Preserve its familiar two-column workflow/status/log composition while improving Future Light branding, accessibility, current operation clarity, product/image/variant progress, errors, and log paging. Keep Swift package/app packaging separate from the Vite build.
- Load only explicitly allowlisted Future Light configuration needed by the safe workflow. Do not parse, use, log, or forward `SALT_*` values or generic Shopify credentials that could target another store. The store identity guard must reject every domain except the exact canonical target confirmed for this project; until the mismatch is resolved, it must fail closed rather than default to either observed domain.
